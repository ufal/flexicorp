ClickCQL Search Guide

ClickCQL is a corpus query language designed for ClickHouse-backed corpora. It is inspired by CQL-style token querying, but it also aims to work well with richer corpus structures such as sentence tables, region tables, dependency information, and tree-sensitive search. In practice, it sits somewhere between familiar token-sequence querying and more explicitly relational or structural searching.

Purpose Of ClickCQL

ClickCQL is used to describe corpus matches in a syntax that remains fairly readable for users who know CQL, while still being suitable for translation into SQL over a ClickHouse corpus schema.

Typical uses include:

  • finding one token or one lemma
  • searching for token sequences
  • searching named query groups whose highlights can be shown separately
  • performing structural or relation-aware searches over sentence-level data
  • using result-oriented commands such as grouping, counts, or tabulation when the environment supports them

Basic Token Queries

ClickCQL often begins with token-style bracket expressions, much like other CQL-family languages.

[lemma="go"]
[upos="NOUN"]
[word="interesting"]

The actual fields depend on the corpus schema and annotation mapping. Common examples include word, lemma, upos, xpos, and dependency-related fields.

Combining Conditions On One Token

Multiple conditions can be combined inside one token expression.

[lemma="go" & upos="VERB"]
[upos="NOUN" | upos="PROPN"]
[lemma!="be"]
  • & means both conditions must be true
  • | means either condition may be true
  • != excludes a value

Regular Expressions

Regular expressions can be used inside token constraints, just as in other CQL-like languages.

[lemma="struggl.*"]
[word="colou?r"]
[xpos="N.*"]

Examples:

  • [word="walk.*"] matches words beginning with walk
  • [upos="NOUN|PROPN"] matches one of two possible categories
  • [xpos="V.*"] matches a family of verbal tags when the corpus tagset uses that convention

Sequences, Gaps, And Repetition

Like CQL, ClickCQL can describe linear token sequences.

[upos="ADJ"] [upos="NOUN"]
[lemma="take"] []{0,3} [lemma="place"]
[upos="ADV"]? [upos="ADJ"] [upos="NOUN"]

The empty token [] means “any one token”. Quantifiers are used in the familiar way:

  • ?: optional
  • *: zero or more repetitions
  • +: one or more repetitions
  • {m,n}: between m and n repetitions

Named Query Groups

One of the important practical features of ClickCQL is the use of named groups. These groups allow the interface to show separate colors and legend entries for different parts of the query.

For example, a query may effectively identify a first token, a second token, or more meaningful named roles, and those groups can then be highlighted separately in the result context.

In the flexiCorp interface, this is what allows the Query groups legend to map onto colored XML result highlights.

Structural And Relation-Oriented Searching

ClickCQL is meant to support more than flat token sequences. In a ClickHouse-backed corpus model, searches can take advantage of sentence-level storage, structural regions, dependency links, and other derived relations. This makes ClickCQL suitable for more tree-sensitive querying than a purely linear token language.

The exact syntax available depends on the current translator and corpus configuration, but the basic idea is that a user-friendly query is translated into SQL over a structured corpus schema.

Why ClickCQL Is Different From Plain SQL

Although ClickCQL ultimately runs through SQL, the user does not normally need to write SQL directly. ClickCQL acts as a higher-level query language that is easier to read and more corpus-oriented. It can then be translated into the appropriate SQL over the underlying ClickHouse tables such as tokens, sentences, docs, or regions.

This separation is useful because:

  • query authors can stay in a corpus-search mindset rather than a database-programming mindset
  • the same corpus concepts can be expressed consistently across different interfaces
  • the system can optimize or reshape the SQL while preserving the intended search semantics

Result-Oriented Commands

Some ClickCQL environments support commands or query types that are not ordinary concordance queries, such as grouping, counts, frequency-style summaries, tabulation, or metadata inspection. In a broader ClickHouse-backed setup, these may map to separate SQL shapes rather than to a simple list of hits.

Depending on the backend and translator support, a query may therefore return:

  • a concordance-style hit list
  • a grouped or counted summary
  • a plain table result
  • metadata such as available regions or attributes

Common Search Examples

An adjective followed by a noun:

[upos="ADJ"] [upos="NOUN"]

A lemma regardless of inflection:

[lemma="go"]

A verb followed within three tokens by a noun:

[upos="VERB"] []{0,3} [upos="NOUN"]

A phrase with optional adverbial material:

[upos="ADV"]? [upos="ADJ"] [upos="NOUN"]

A token constrained by more than one field:

[lemma="bank" & (upos="NOUN" | upos="PROPN")]

ClickCQL And Tree-Sensitive Search

One of the longer-term motivations for ClickCQL is that many corpora now support richer syntactic or dependency-oriented querying. In such cases, the result may no longer be a simple contiguous token sequence. A query may identify several important tokens that belong together structurally but are not adjacent in surface order.

This has consequences for result presentation:

  • plain KWIC works well for contiguous sequence matches
  • table or grouped XML views are often better for structural matches
  • anchor-KWIC can be useful when one matched group should be treated as the central focus

Things To Keep In Mind

  • ClickCQL is corpus-oriented syntax that is translated to SQL; it is not just “SQL with brackets”.
  • Attribute names still depend on the corpus and its mapping into the ClickHouse schema.
  • Some query forms return ordinary hits, while others return table-like summaries.
  • Named query groups are especially important because they drive colored legends and result highlighting.
  • Tree-sensitive or discontinuous matches may be better shown in grouped or table displays than in plain KWIC.

When To Use ClickCQL Instead Of SQL

Use ClickCQL when you want to express a search in corpus terms rather than in raw database terms:

  • token sequences
  • annotation constraints
  • query groups that should be highlighted separately
  • corpus-specific structural patterns

Use SQL only when you specifically want direct database inspection or a custom analytic query that falls outside the supported ClickCQL translator.
