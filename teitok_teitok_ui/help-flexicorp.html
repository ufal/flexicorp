flexiCorp Interface Guide

This page explains the user-facing options exposed by flexicorp.php, the TEITOK / EasyCorp interface for comparing corpus backends, query languages, and result presentations through the shared flexicorp CLI.

What This Interface Is For

The flexiCorp page is meant as a corpus search test bench. It lets you compare different combinations of:

  • backend, such as cqp, flexi, clickql, or clickhouse
  • query language, such as cwb-cql, clickcql, pmltq, or sql
  • storage / execution engine, such as cwb, clickhouse, or manatee

Depending on the corpus, not every combination is available or exposed. The page only offers combinations that the current configuration makes visible.

Top-Level Layout

The interface is divided into tabs:

  • Overview: shows which backend / query-language / storage combinations are available
  • Documents: lists the corpus documents that the current backend can return
  • Search: runs queries and displays concordance-style results
  • Frequency: exposes backend frequency-list support
  • Debug: admin-only diagnostics for the actual calls made by the page

Overview Tab

The Overview tab presents the combinations returned by flexicorp info backends. Each row contains:

  • Backend: the implementation used to execute the request
  • Query language: the query syntax expected for search operations
  • Storage / engine: the underlying corpus format or execution engine
  • Status: whether the combination is currently usable
  • Reason: a short explanation of why it is available or unavailable
  • Use: switch the page to that combination
  • Status: show the structured status payload for that combination

If external engines are configured for the corpus, they are shown below as links to interfaces such as Kontext, NoSketchEngine, Grew, or PML-TQ.

Search Header

The Search tab is the main interactive part of the interface.

Search Query

This is the query text that will be sent to the currently selected backend. Next to the label, the page shows the current query language. If there are multiple visible query-language options for the current backend, a selector is shown there so you can switch between them without going back to the Overview tab.

If a help page exists for the current language, its name becomes a link. For example:

  • cwb-cql links to help-cwb-cql
  • pmltq links to help-pmltq

Changing the query-language selector may also change the associated corpus format, because some languages are only valid for one backend / storage combination.

Hit Limit

This controls how many results are requested and rendered on the page initially. The Show more button requests a larger slice later.

Syntax Highlight Query

This enables live syntax highlighting of the query text when the current backend supports it. At the moment this is mainly useful for flexi, cqp, and clickql. Highlighting may slow typing somewhat because it triggers background parsing / highlighting requests.

Context Options

Context Format

  • xml: request TEITOK / structured XML-style context where available
  • raw: request non-XML context, typically closer to the native engine output

In XML mode, the page tries to render structural context and highlight matched tokens inside it. In raw mode, the display stays closer to the underlying search engine output.

Context Scope

This defines which region should be extracted around a hit. The options are offered as a dropdown rather than a free-text field, and they are derived from the corpus metadata that the current backend exposes.

Typical region choices are:

  • sentence / s
  • paragraph / p
  • document / text

For backends that support classic engine-side token windows, the dropdown may also contain token window. That option means “show a fixed number of tokens to the left and right of the hit” rather than extracting a named structural region such as a sentence.

Sentence context is often the most useful default for tree-sensitive searches, because syntactic matches are usually sentence-bound. Token windows remain useful for users who prefer a traditional KWIC experience or for corpora that do not provide sentence boundaries.

Display

This controls how the results are rendered on the page.

  • Grouped context: groups hits by document and merges repeated contexts when possible
  • Table: one compact row per occurrence
  • KWIC: classic left / match / right display, centered on the matched token span
  • Anchor KWIC: shown only when supported by the current result set; centers the KWIC around an anchor group for discontinuous matches

Not all result shapes are equally suitable for KWIC. If a query finds discontinuous matches, plain KWIC can become misleading because it may place unmatched material between the first and last matched tokens. In those cases the interface may expose Anchor KWIC as an alternative centered on a more meaningful token or group.

Result Presentation

Grouped Context

This view groups results by document and shows each context block once. If several hits fall in the same rendered context, their highlights are merged.

Table View

This view gives a compact one-row-per-occurrence summary. It is useful when you want to inspect many hits quickly without the broader grouped layout.

KWIC And Anchor KWIC

These views split the result into:

  • left context
  • match or anchor
  • right context

The left and right context columns are deliberately clipped to keep rows compact. In XML-based KWIC rendering, the clipping is done so that the text nearest the match remains visible.

Query Groups Legend

If the backend returns named highlight groups, the page shows a legend above the results. In XML rendering, matched tokens are colored to follow that legend. This is especially useful for multi-part queries and tree- or relation-oriented searches.

Documents Tab

The Documents tab shows document-level metadata returned by the current backend. The exact fields depend on what the backend can provide. For smaller corpora, the page can let client-side tooling handle sorting and filtering; for larger corpora, it keeps the interaction simpler.

Frequency Tab

This tab exposes backend support for frequency-style operations. It is primarily intended for development, comparison, and inspection rather than for a polished end-user interface. The field and limit options are passed through to the backend.

Raw Buttons

Several tabs have a Raw button. This opens a dialog showing the underlying command, raw payload, warnings, and other diagnostic information. It is mainly meant for development and debugging.

Help Button

The top-level Help button opens an in-page overview of the interface. This document provides the more detailed, field-by-field explanation.

Settings Dialog

The Settings dialog currently controls interface defaults such as:

  • backend
  • document limit
  • default hit limit
  • default KWIC / token-window size
  • default frequency limit

At present, this dialog is mainly about UI defaults for the current page. It is not yet a full persistent corpus-configuration editor.

Debug Tab

For admin users in debug mode, the Debug tab lists the actual flexiCorp calls made during the page session, together with their commands, warnings, errors, and result payloads.

How Combination Selection Works

The interface always runs with a logical triple:

  • backend
  • query language
  • corpus format / execution engine

In some cases there is more than one valid query-language option for the same backend. The search header selector lets you switch between those currently visible combinations. In future configurations, it should be possible to keep some combinations available in the system but hidden from non-admin users; the selector is designed to respect that model by using only the combinations exposed to the page.

Things To Keep In Mind

  • Not every backend supports every operation equally well. Some combinations are excellent for concordances, others for frequency lists, tree search, or SQL-style inspection.
  • Different context formats and context scopes can change the shape of the rendered result quite a lot.
  • KWIC is not always the best display for discontinuous or strongly structural matches.
  • If a query returns a non-concordance structure such as a table, the page will switch to table-style rendering.
  • The precise set of options depends on the current corpus configuration and which backend combinations are exposed.

Suggested Workflow

  1. Pick a combination on the Overview tab.
  2. Write a query in the Search tab and, if helpful, enable syntax highlighting.
  3. Choose XML or raw context depending on whether you want structure-aware rendering or engine-native output.
  4. Choose a context scope suited to the corpus and the query type.
  5. Use Table, Grouped, KWIC, or Anchor KWIC depending on the result shape.
  6. Use Raw or Debug views when you need to inspect the actual backend behavior.
