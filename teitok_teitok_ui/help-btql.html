BTQL Search Guide

BTQL is intended for tree- and dependency-oriented searching rather than flat token-sequence searching. It is especially relevant for corpora with Universal Dependencies or similar parsed annotation, where you want to describe relations such as head, dependent, child, parent, or subtree structure.

Purpose Of BTQL

Where a token query language such as CQL asks “which tokens or token sequences match this pattern?”, BTQL asks “which nodes in the dependency structure match this pattern, and how are they related?”. This makes it suitable for searches such as:

  • a noun with an adjectival dependent
  • a verb with a subject child
  • a node whose parent has a certain feature
  • a dependency relation such as nsubj, obj, or amod

Typical Data Needed

BTQL-style searching generally assumes that a corpus contains parsed structure, not just token attributes. In a UD-style corpus, useful fields often include:

  • form or word
  • lemma
  • upos and sometimes xpos
  • deprel
  • head or another way to identify the governing node
  • sentence boundaries, because dependency trees are sentence-based

Basic Node Constraints

Like other tree-query languages, BTQL normally starts by selecting one node with certain attribute values.

[upos="NOUN"]
[lemma="go"]
[deprel="nsubj"]

These examples describe one node that must satisfy the given condition.

Dependency Relations

The main reason to use BTQL is not just to test one node’s attributes, but to express relations between nodes. In a dependency tree, this often means conditions such as:

  • a node has a child with some property
  • a node has a parent with some property
  • a node has a dependent with a particular dependency label
  • two nodes are linked by a head-dependent relation

For example, the linguistic ideas behind BTQL-style searches would include patterns such as:

a NOUN with an ADJ dependent
a VERB with an nsubj child
a token whose parent is a VERB
a node with deprel="obj" governed by a certain lemma

Why Sentence Structure Matters

Dependency relations are sentence-internal. A BTQL-capable index therefore normally needs sentence spans and a way to resolve which node governs which other node. Without that structural layer, a backend may still let you search token attributes such as deprel, but not true dependency paths.

Examples Of Linguistic Questions

  • Which adjectives modify a noun?
  • Which verbs take a nominal subject and an object?
  • Which nouns occur as subjects of a given lemma?
  • Which adverbs modify adjectives rather than verbs?

Relation To Other Query Languages

BTQL belongs with structural query languages such as PML-TQ rather than with token-sequence languages such as CQL. In practice:

  • use CQL when you care about surface order and adjacency
  • use BTQL when you care about dependency structure
  • use PML-TQ or similar languages when you need richer tree or graph conditions

What To Keep In Mind

  • BTQL-style search depends on parsed corpus structure, not just plain tokenization.
  • Fields such as head and deprel are necessary, but by themselves they are not always enough; the backend may also need explicit structural indexing.
  • Sentence boundaries matter, because dependency trees are sentence-based.
  • Support depends on both the corpus backend and how the corpus was indexed.

Current flexiCorp Note

BTQL is best understood as a dependency-search language for parsed corpora. Whether a given corpus can actually execute BTQL-style structural searches depends on the backend and on the index. Some current backends may only expose dependency-related annotations such as deprel as token attributes, without yet supporting full structural traversal.
